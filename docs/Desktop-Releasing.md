# 桌面 SDK 发布

桌面 SDK 随仓库的 `v*` 标签发布，由 [Release 工作流](../.github/workflows/release.yml) 调用 [Desktop SDK Release](../.github/workflows/desktop-release.yml)。调用库与原生运行时使用同一版本；CI 从标签提取版本，在构建目录中更新清单，不需要逐个修改桌面包的开发版本。

## 发布内容

| 渠道 | 制品 |
| --- | --- |
| npm | `@dimina/desktop-sdk`，包含 Node/Electron 入口和 Tauri 前端入口 |
| crates.io | `tauri-plugin-dimina` |
| NuGet | `Dimina.Desktop` |
| GitHub Release | 各平台完整 SDK 包、上述调用库制品及 `SHA256SUMS-desktop.txt` |

运行时在目标系统原生构建，macOS 仅发布 ARM64，Windows 和 Linux 发布 x64、ARM64。GitHub Release 中的 SDK 包命名为 `dimina-desktop-sdk-{version}-{os}-{arch}.tar.gz`，Windows 使用 `.zip`；架构名称为 `amd64` 或 `arm64`。

每个 SDK 包包含 `runtime/`、Node 调用库、Qt CMake 源码、.NET 项目、Tauri 插件和许可证。macOS 压缩包保留完整 `.app`、符号链接和可执行权限；Windows/Linux 按运行时的安装文件清单收集依赖，避免把中间安装包重复打进去。`version.json` 记录版本与目标平台。

## 首次配置

三个 registry 使用 **Trusted Publishing（OIDC）**：GitHub Actions 在发布任务中取得短期凭据，无需保存或定期更换 npm、crates.io、NuGet 的长期 Secret。发布账号须拥有对应包名或作用域，并在各 registry 配置对 `didi/dimina` 的信任。

| 渠道 | Trusted Publisher 配置 | 工作流认证 |
| --- | --- | --- |
| npm | 包 `@dimina/desktop-sdk` 的 Settings → Trusted publishing；GitHub owner `didi`、repository `dimina`；分别添加 `release.yml` 和 `desktop-release.yml`，允许直接 `npm publish` | npm CLI 自动取得 OIDC 凭据；工作流固定使用支持 OIDC 的 npm 12.2.2，发布时生成 provenance |
| crates.io | crate `tauri-plugin-dimina` 的 Settings → Trusted Publishing；owner `didi`、repository `dimina`；分别添加 `release.yml` 和 `desktop-release.yml` | 官方 `rust-lang/crates-io-auth-action@v1` 换取 30 分钟 Token，并在任务结束时撤销；上传已验证的 `.crate`，不重新构建 |
| NuGet | 账号的 Trusted Publishing；Package Owner 选择包所有者，Repository Owner `didi`、Repository `dimina`、Workflow File **`desktop-release.yml`**；仅允许 Push，包模式精确填写 `Dimina.Desktop` | 官方 `NuGet/login@v1` 换取一小时 API Key；仓库 Actions **Variables** 中设置 `DESKTOP_NUGET_USER` 为策略所属的 NuGet 用户名（非邮箱） |

两种入口的身份规则不同：npm 和 crates.io 校验调用方 `workflow_ref`，自动 Release 对应 `release.yml`，直接手动执行对应 `desktop-release.yml`；NuGet 校验 `job_workflow_ref`，两种入口均对应实际执行发布的 `desktop-release.yml`。文件名区分大小写，只填文件名。当前任务未声明 GitHub environment，registry 中的 Environment 留空；以后添加 environment 时须同步调整信任条件。调用方与发布任务均须保留 `id-token: write`。依据：[npm 官方说明](https://docs.npmjs.com/trusted-publishers/)、[crates.io 身份解析](https://github.com/rust-lang/crates.io/blob/main/crates/crates_io_trustpub/src/github/claims.rs)、[NuGet 身份验证器](https://github.com/NuGet/NuGetGallery/blob/main/src/NuGetGallery.Services/Authentication/Federated/GitHubTokenPolicyValidator.cs)。

**包尚未存在时，不能把上述配置视为已完成。** npm 和 crates.io 目前要求先发布一次包，之后才能在包设置中添加 Trusted Publisher。首次发布应使用经检查的真实版本与制品：npm 可使用账号交互认证；crates.io 需要仅限目标 crate 的临时发布 Token，使用后撤销。不为占位而发布空包，也不将首发凭据保存成长期 Actions Secret。先运行下述 `dry_run` 检查制品，再单独完成首次发布和信任绑定。npm 新建的绑定须在 **2 天内**成功发布一次，否则会过期；完成首轮验证后不受此初始期限限制。NuGet 可在包首发前配置精确包模式；暂时性策略应在页面显示的验证期限内完成首次发布。参考：[crates.io 前提条件](https://crates.io/docs/trusted-publishing)、[npm 配置及初始期限](https://docs.npmjs.com/trusted-publishers/)、[NuGet Trusted Publishing](https://learn.microsoft.com/en-us/nuget/nuget-org/trusted-publishing)。

测试、构建、打包及 GitHub Release 附件发布不依赖 registry 认证。各渠道独立认证和发布：信任或账号配置不完整的渠道会失败，不影响其他渠道和 GitHub 附件，也不会被标记为已发布。`dry_run` 不请求 OIDC 凭据、不执行 registry 发布；GitHub Release 使用工作流内置授权。短期凭据只在发布任务内使用，不写入源码、制品或日志。原 `DESKTOP_NPM_TOKEN`、`DESKTOP_CARGO_REGISTRY_TOKEN`、`DESKTOP_NUGET_API_KEY` 不再被读取；已有长期凭据应在完成 OIDC 发布验证后撤销。

首次创建 npm/crates.io 包时，使用最短可用有效期和最小范围的临时凭据，分别写入 `DESKTOP_NPM_BOOTSTRAP_TOKEN`、`DESKTOP_CARGO_BOOTSTRAP_TOKEN`。只在手动运行 **Release** 或 **Desktop SDK Release** 时将 `bootstrap_registries` 设为 `true`；默认流程继续使用 OIDC。npm bootstrap 配置文件仅引用环境变量，保留 CI provenance；Cargo 继续上传经验证的原始 `.crate`。首发成功后配置 Trusted Publisher，立即撤销临时凭据并删除这两个 Secret，以后的发布保持该开关为 `false`。

Cargo 打包前执行 `cargo check`，让 Tauri 先生成 `permissions/autogenerated` 和 `permissions/schemas`。这些文件由清单中的 `permissions/**` 一并打入 crate，使解压后的完整构建验证不会再新增源码文件；保留 `cargo package` 的默认验证。

## 发布前验证

日常分支推送和 PR 会触发 [Desktop Tests](../.github/workflows/desktop-tests.yml)，也可在 Actions 中手动运行。它在 Windows 2025 x64、Ubuntu 24.04 x64、macOS 15 ARM64 上分别执行，无需发布凭据。正式发布复用同一测试流程，全部通过后才会上传制品。

| 范围 | CI 执行内容 |
| --- | --- |
| Go 运行时 | HTTP/文件传输、TCP/UDP 回环连接、文件授权、存储持久化、原生桥接身份与取消；macOS/Linux 启用 race 检查 |
| 前端 | 公共列表、Web 容器、桌面适配与 API 注册回归 |
| Node / Electron、Tauri | 使用原生测试进程验证握手、标准输入输出通信、错误、取消、关闭超时及子进程回收；Node 类型检查 |
| Qt / .NET | 各系统原生编译并执行 SDK 进程生命周期用例；Qt 使用 Qt 6 |
| BLE helper | 状态转换、取消、超时和通知协议的单元测试 |

Node 和 Rust SDK 用例共用可跨平台编译的测试运行时，Windows 不再跳过这些进程协议测试。测试运行时不创建 WebView 窗口，不代替真实桌面运行时的界面验收。相机扫描、真实 BLE 连接、系统权限弹窗、窗口视觉和焦点行为仍需目标设备或具备相应硬件的 runner 验证。三系统测试日志保存在 `test-results-desktop-*` Actions artifacts；发布构建覆盖 macOS ARM64 以及 Windows、Linux 的 x64/ARM64。

将流程配置合入后，在包含该配置的提交上创建发布标签。在 Actions 中手动运行 **Desktop SDK Release**：

- `release_tag`：已有标签，例如 `v1.9.0-beta.1`。
- `dry_run`：保持 `true`。

工作流校验 checkout 与标签一致，执行 Node/Tauri 前端、Rust、BLE helper、Qt、.NET、桌面前端和 Go 检查，并构建六组运行时。全部完成后，`desktop-release` Actions artifact 提供完整制品和校验和，供下载检查。此模式不会创建 GitHub Release，也不会向 registry 上传。

## 正式发布与重试

推送 `v1.2.3` 或 `v1.2.3-beta.1` 格式的标签会由主 Release 流程自动发布桌面 SDK。也可以针对已有标签手动运行 **Desktop SDK Release**，将 `dry_run` 设为 `false`。发布阶段等待所有 SDK 检查和五个平台构建通过；先上传 GitHub Release 附件，再分别发布各 registry 的调用库。完整发布需所有渠道成功；只有附件成功时，仍可下载 SDK 包中的调用库进行接入。

稳定版本使用 npm 的 `latest` 标签；预发布版本使用 `next`，GitHub Release 同时标记为 prerelease。标签不接受 SemVer build metadata（`+...`），以避免不同 registry 的版本规范化产生歧义。

重试时优先使用 **Re-run failed jobs**，复用本次已经验证的构建产物。已有 GitHub 附件、npm 包或 Cargo 包只有在校验和相同时才跳过；内容冲突会失败，不会覆盖。NuGet 使用 `--skip-duplicate` 跳过已发布的版本。完整重跑会重新构建运行时，压缩包可能因构建时间等信息产生不同校验和；需要更改已发布内容时，应使用新版本。

补齐信任配置后，可重跑对应的失败任务。若修改了工作流本身，应从包含该修改的分支手动启动 **Desktop SDK Release**，指定已有的 `release_tag`；旧运行的重试仍使用原工作流版本。

各 registry 独立发布，无法跨服务原子提交；部分发布失败后，可补跑对应失败任务。制品校验和只覆盖桌面附件，不替换其他平台已有的校验文件。

## 集成产品签名

这些运行时用于集成到现有客户端，不是独立客户端安装器。CI 默认使用桌面构建工具的 ad hoc macOS 签名；不配置 Developer ID、公证凭据或 Windows 代码签名证书。接入产品仍需按自身分发方式完成运行时签名、公证及系统依赖准备，见 [SDK 产品分发说明](../desktop/sdk/README.md#发布到已有产品)。
